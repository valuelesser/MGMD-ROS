## 1. Executive Summary

我要在 **ARD-MAV 数据集**上复现 MGMD 三模块流水线（MFE 运动特征增强 → TF 轨迹过滤 → LAC 局部外观分类 → LAD 局部外观检测），产出可直接与论文 Table 1 / Table 2 / Table 3 并排对比的表格，并提交一份逐项说明"哪些数字可比、哪些不可比"的偏差报告。

**这份 PRD 的核心不是"照着写代码"，而是先定义"什么算复现成功"。** 这篇论文没有发布官方代码、没有给出帧间隔 k、没有说明 LAC 训练样本如何构造、没有定义 AP 的计算方式。

好消息是：**测试集划分已经找到了**。论文正文只说"50 训练 / 10 测试"不给 ID，但同组 GLAD 仓库的 README 公开了 15 个测试视频 ID 并按 Ordinary/Complex/Small 分了三档，这 15 个视频在本地数据里全部齐全。所以我们不用自建划分。

坏消息是：**论文的 D≥1 判据数学上不可达**（我用 28,096 对真实 GT 验证，0 个通过，见 §6.0）。这是复现过程中发现的论文缺陷，本身要作为结论报出来。

结论先行：**论文数值不可能逐位对齐，但三张表的趋势和量级可以复现。** PRD 以此为验收基准（§6），超出带宽即判失败并强制归因。

### 1.1 阶段二：从离线复现到实机系统（本版新增）

阶段一交付的是"在别人的数据集上把论文跑出来"。阶段二要把同一套算法搬到真实旋翼平台上：

> 利用 DJI RoboMaster TT 四旋翼无人机，使用基于其 Python SDK 的 ROS 驱动，实现单目旋翼无人机小目标检测与跟踪。各功能以 ROS 节点形式模块化实现，完成易于扩展的检测跟踪软件框架。

**这不是"加个摄像头读帧"那么简单。** 三个变化会重构整个交付物：

| 变化 | 阶段一 | 阶段二 |
|---|---|---|
| 输入 | 1080p 机载俯视数据集 | 960×720 前视 WiFi 视频流 |
| 运行方式 | 离线批量处理 | 在线逐帧，有硬延迟上限 |
| 交付形态 | 脚本 + 报告 | 可启动的组合式软件系统 |
| 失败代价 | 指标不好看 | 炸机 |
| 飞场 | 无 | **室外场地**，风、逆光、天空背景 |

结论先行：**阶段二有四个技术风险，按严重度排序：**

1. **ROS1 Noetic 绑死 Python 3.8**，阶段一算法跑在 3.11。这决定整个节点架构（§11.0.1）。
2. **Tello 相机 vs ARD-MAV 的域差异**，现有 LAC/LAD 权重很可能直接失效，必须用实拍数据微调（§11.4 约束 2）。
3. **室外飞行的安全边界**：多机同场、无定位系统、WiFi 干扰。软件必须能在丢图传时自保（§11.4 约束 6）。
4. **ROS1 驱动生态的不确定性**：Tello/TT 的 ROS1 驱动没有官方维护版本，需自写或依赖第三方（§11.2）。

好消息是 **Q20/21 已确认实验室有多架无人机、Q23 已确认室外场地**，"目标机从哪来"和"在飞场还是室内"两个前置问题都解决了。剩下的是工程问题，不是前提问题。

`[flag: 用户原始表述是"利用 DJI RoboMaster TT 四旋翼无人机"，单数。但 Q20 回答是"实验室提供的无人机有多个"。本 PRD 按"≥2 架"设计：一架观察者（挂相机），至少一架目标机。若实际只有一架 TT 且其余是别的机型，目标外观域差异会更大，§11.4 约束 2 的微调量要相应加大。]`

## 2. Problem Statement

**谁有这个问题**：我自己，一个人做毕业设计的复现者。手上有论文 PDF/Markdown、有一台消费级笔记本（RTX 3050 4 GB，已实测够用）。工时估算约 34 人天 ≈ 5.5 周（§9.1b，含代码复用）。

**问题是什么**：论文给的是方法描述 + 三张结果表，缺的是可执行规格。缺失项不是边角料，是决定结果的参数：

| 缺失项 | 影响 | 论文是否提及 |
|---|---|---|
| 帧间隔 k（当前帧与前后各 k 帧做差分） | 直接决定 MFE 能否检出 8×8 像素目标 | ❌ 完全未给 |
| 测试集划分（论文只说 50 训练 / 10 测试） | 论文未给 ID，**但 GLAD README 给了 45/15 及 15 个 ID** | ⚠️ 论文未给，同组仓库给了（且两者数字冲突） |
| LAC 正负样本构造方式 | 决定 LAC 能否学到 MAV 与杂波边界 | ❌ 未说明 |
| LAD "小目标检测层"具体接法 | 只说"浅层与深层 concat" | ⚠️ 一句话，无结构 |
| AP 计算口径（按帧累积 vs 按视频） | 0.55 这个数字无从核对 | ❌ 未说明 |
| FPS 是否含预处理 | 28 FPS 的边界不明 | ❌ 未说明 |

**为什么痛**：这六项里任意一项选错，结论就从"复现成功"变成"实现有 bug"。没有事先约定的验收带宽，我会在"是不是我写错了"和"是不是论文没写清"之间反复消耗工时，最终交付一份无法自证的报告。

## 4. Strategic Context

**为什么现在做**：数据已齐全（60 视频 / 107,497 XML，与官方 README 逐数字核实）、权重已下载、官方测试集划分已拿到、论文的 D 判据缺陷已定位。前一个工程失败的原因也清楚了（见下）。这是把所有不确定性清掉之后，第一次可以干净地重做。

**前一个工程（`…/mgmd/`）的失败模式，是本项目最重要的输入**：

| 它做了什么 | 为什么失败 |
|---|---|
| MFE 跑出 71.2% 召回 | 但其中混入了四项论文没有的额外约束（高斯模糊、位移过滤、面积上限、长宽比），无法归因 |
| TF 判据 D≥1 跑不通 | 没有停下来问"是不是公式本身有问题"，而是改了实现 |
| 最终放弃 | — |

**`tracking/` 是另一个前项目，失败模式不同但同样有参考价值**：

| 它做了什么 | 为什么不能用 |
|---|---|
| 把 `alg1_d_min` 从 1.0 降到 0.002–0.1，每序列一个值 | 实测降阈值后 Algorithm 1 只剩 **0.59%** 剔除率，机制等于关掉；且对着测试集调参 |
| 加了论文没有的 `ever_confirmed` 粘性标志 | 偏离论文，未声明为偏离 |
| MVDT 上跑到 95.96% recall | 点 GT + 半径 100px 匹配，与论文框 GT + IoU 0.25 口径不可比 |

**所以本项目的核心战略是：把"方法是否奏效"和"参数是否调对"彻底分开。** 具体三条：

1. **额外约束必须做开关对照**。任何论文没有的步骤，都要给出"开 vs 关"两行数字。
2. **阈值只能从训练集标定**，测试集不参与，且全测试集用同一个值。
3. **论文原值必须报**。`d_min=1.0` 那行如实写"0 条轨迹通过"，这是论文缺陷的直接证据，不是我们的失败。

## 5. Solution Overview

### 5.1 复现流水线（四模块，二阶段策略）

```
ARD-MAV 视频 + VOC XML
        │
        ▼  [新增] 数据适配层：视频 ↔ XML 帧号对齐，统一 GT CSV
        │
        ▼  MFE ── 网格 LK + RANSAC 单应 → 多帧差分（k 可配）→ OR 聚合 → 形态学 → 连通域
        │
        ▼  TF  ── SORT（IoU 0.3、max_age 3、min_hits 1）+ Algorithm 1（ρ/d ≥ d_min，双模式）
        │
        ▼  LAC ── 32×32 三层 CNN 二分类（阶段A 官方权重 / 阶段B 自训）
        │
        ▼  LAD ── 320×320 裁剪 + YOLOv5s(+小目标层)（阶段A 官方权重 / 阶段B 自训）
        │
        ▼  [新增] 评测层：IoU 0.25 匹配 → P/R/F1/AP/FPS
        │
        ▼  Table 1 / Table 2 / Table 3 + 偏差归因报告
```

**阶段 A（第 1–4 周）**：用 GLAD 仓库官方权重（在 ARD-MAV 上训练）跑全流水线，先拿到端到端基线。目的不是"复现成功"，而是**证明评测链路正确**：如果阶段 A 的 F1 已经掉到 0.4 以下，问题在评测或数据对齐，不在训练。

**阶段 B（第 5–5.5 周）**：按论文配方自训 LAC（Adam lr=0.001、100 epochs、batch=64、32×32）与 LAD（YOLOv5s + 小目标层、Adam momentum=0.937、lr=0.01、MS-COCO 预训练、320 裁剪）。阶段 A 与 B 的结果**并列呈现**，不合并。

| 项 | 判断 |
|---|---|

## 6. Success Metrics

### 6.0 两个必须先解决的已发现问题（决定复现是否成立）

你已有的实测数据暴露了两个**结构性矛盾**，它们比"跑出多少 F1"更重要。这两个不解决，Table 1/3 数字没有意义。

**问题 A：论文的 D≥1 判据在 ARD-MAV 上数学不可达（已独立验证，非引用）**

论文英文原文（`paper_mgmd_en.md` 第 118 行）定义：

> $d(b_i,b_j)$ represents the diagonal length of the **smallest enclosing box** of $b_i$ and $b_j$.

**证明（纯数学，与实现无关）**：设两框中心距为 ρ，最小外包框宽 W、高 H，对角线 d=√(W²+H²)。
若 b_j 在 b_i 右侧，则 W = (x1j+wj) − x1i，而 ρ = (x1j+wj/2) − (x1i+wi/2)。
两式相减：**W − ρ = (wi+wj)/2 > 0**，故 ρ < W ≤ d，**即 D = ρ/d < 1 恒成立**。
这个不等式对任意框尺寸、任意位移都成立，与数据集无关。

**三重独立验证**：

| # | 验证方式 | 结果 |
|---|---|---|
| 1 | 数学证明（上式） | D < 1 恒成立，仅当框退化为零尺寸点时极限为 1 |
| 2 | 随机生成 20 万组框对 | D 最大观测值 **0.9731**，无一达到 1 |
| 3 | **28,096 对真实 GT**（15 个官方测试视频全部，间隔 3 帧，单目标帧） | D 最大 **0.9610**，`D≥1` 通过 **0 个（0.000%）** |

逐视频最大 D：phantom43 0.9540、phantom58 0.9610、phantom05 0.9073、phantom10 0.8919…… **15 个视频无一有帧达到 1。** 验证脚本：`paper/_verify/realD.py`、`percentiles.py`、`target_motion.py`，可复跑。

**为什么论文能出结果？** 因为 D≥1 隐含了一个前提：**3 帧内位移 ≥ 目标自身尺寸**。实测该前提在 ARD-MAV 上不成立：
位移/尺寸比的 P50 只有 **0.478**，仅 **16.41%** 的样本位移超过自身尺寸。论文的 D≥1 阈值实际等价于只保留"极快运动"的目标。

**D 的真实分布**（N=28,096）：

| 分位 | P50 | P75 | P90 | P95 | P99 | max |
|---|---|---|---|---|---|---|
| D | 0.332 | 0.459 | 0.579 | 0.655 | 0.781 | 0.961 |

若改用标定阈值：thr=0.5 → 保留 18.69%；thr=0.6 → 8.44%；thr=0.7 → 3.20%；thr=0.8 → 0.72%。

`[flag: 这是独立发现，不是"我们实现错了"。论文公式与其阈值 D≥1 在数学上不自洽。必须在报告中作为独立发现列出，并给出标定阈值的对照。]`

**问题 B：MFE 漏检是瓶颈，不在 TF**

实测：phantom63 背景极杂乱（213 候选/帧），phantom76 极干净（7.9 候选/帧），**候选数降 27 倍，轨迹碎片率几乎不变（63% vs 60%）**。

逐帧定位断点：帧 319/325/327 的 MFE **候选数为 0**（完全漏检）；帧 322–323 检出了但框偏大（20×13 vs GT 14×10），IoU 掉到 0.25 以下。

**结论：优化 SORT 关联策略解决不了碎片化。MFE 的检出稳定性必须先解决。** 这直接推翻原 PRD "G1 候选召回 ≥70% 就算过"的设计——70% 的召回意味着 30% 的帧直接无输入。

### 6.0b 一个被推翻的结论：`Net_best.pth` 没有失效

旧工程在 TODO.md 里断言：`Net_best.pth` 对所有输入恒返回类别 0，"权重失效，必须重训"。**这个结论是错的，我推翻了。**

**复验方法**：把 checkpoint 的 fp32 权重直接从 zip 里解出来，用纯 Python 实现一遍前向传播（Conv5×5 → MaxPool2 → Conv5×5 → MaxPool2 → FC400-120-84-2，与官方 `Net` 逐层一致），喂真实数据。

**第一层验证：权重的物理完整性**

| zip 容器完整性 | ✅ `testzip()` 通过，12 个条目 |
| 各层形状与代码 `Net` 定义对比 | ✅ 10/10 全部匹配（conv1 450、conv2 2400、fc1 48000、fc2 10080、fc3 168） |
| `fc3.bias` | `(-0.0426, -0.0472)`，两个类别偏置几乎相等，不偏袒任何一类 |

### 11.0.2 架构约束：ROS1 Noetic 绑死 Python 3.8

这条约束决定一切，必须先讲清楚。

**事实**：ROS1 Noetic 的 Python 端只支持 Python 3.8。`rospy`、`tf2_ros`、`cv_bridge`、`sensor_msgs` 全部安装在 `/usr/lib/python3/dist-packages`，只能被 `/usr/bin/python3`（3.8.10）导入。

**冲突**：阶段一的算法环境是 `.venv` 里的 **Python 3.11.17 + torch 2.5.1+cu121**。3.8 装不了 torch 2.5，能用的是 torch 1.13（cu117）。

**三个方案对比**：

| 方案 | 做法 | 工时 | 致命问题 |
|---|---|---|---|
| **A sidecar** | ROS 节点跑 3.8；检测进程独立跑 3.11，走本地 socket | 2–3 天 | 进程间要定义协议（已设计，见下） |
| B 双解释器 | 相机节点 3.8，检测节点 3.11 手动装 rospkg | 2 天 | 跨版本传 `sensor_msgs/Image` 要手写序列化，`cv_bridge` 用不了 |
| C 全降到 3.8 | 重装 torch 1.13，重导 TRT engine | 5 天 + 1 天重导 | **阶段一已跑通的全部结果要重跑验证**，风险不可控 |

**采用 A。** 理由不是"工时最短"，是"唯一不碰已验证环境"的方案。阶段一的 62 项测试、F1=0.658 的结果、TRT engine 全部原样保留在 3.11 环境里，一个字节不动。

**代价必须说清楚**：多了进程边界，调试要跨进程看日志；多一次内存拷贝（960×720×3 ≈ 2 MB/帧，本地 socket 约 1–2 ms，可忽略）。

### 11.1 架构：五个 ROS1 节点 + 一个 sidecar

```

│  ROS1 主图（Python 3.8）                                          │
│                                                                  │
│  ┌─────────────┐                                                 │
│  │ tt_driver   │──► /camera/image_raw (sensor_msgs/Image, bgr8)  │
│  │ (djitellopy)│──► /tt/state            (Float32MultiArray)     │
│  └─────────────┘◄── /tt/cmd_vel          (geometry_msgs/Twist)   │
│         │                                                        │
│         ▼                                                        │
│  ┌─────────────┐                                                 │
│  │ mav_node    │──► /mav/candidates ──┐                          │
│  │ (socket     │──► /mav/detections ──┤                          │
│  │  client)    │◄── socket ───────────┼──┐                       │
│  └─────────────┘                      │  │                       │
│                                       │  │  ┌──────────────────┐ │
│  ┌─────────────┐                      │  └─►│ detect_server.py │ │
│  │ tracker_node│◄─────────────────────┘    │ (Python 3.11)    │ │
│  │  (SORT)     │──► /mav/tracks            │ MFE→TF→LAC→LAD   │ │
│  └─────────────┘                            └──────────────────┘ │

│         ▼                                                        │

│  ┌─────────────┐                                                 │
│  │mission_node │◄── /mav/tracks  ──► /tt/cmd_vel  (视觉伺服)     │
│  └─────────────┘                                                 │
└──────────────────────────────────────────────────────────────────┘
```

**为什么 MFE 和 TF 也在 sidecar 里，而不是在 ROS 节点里？**

MFE 用 `cv2`（纯 CPU，3.8 也能跑），TF 是纯 Python（3.8 完全兼容）。理论上它们可以留在 ROS 侧，只有 LAC/LAD 需要 3.11。但我**不这么拆**，原因是：

阶段一的 `pipeline.run()` 是**一个整体**：MFE 输出 `step_H`（帧间单应）给 TF 做 Algorithm 1 对齐，TF 的输出候选再喂 LAC/LAD。这三步之间有数据依赖（`step_H`、候选顺序），拆到两个解释器就要把 `step_H` 也序列化过去，等于把内部接口暴露成协议。

**整段留在 sidecar 里，ROS 侧只看输入帧和输出检测。** 这样 sidecar 的协议只有两样东西：帧进去，检测出来。简单到不会出错。

`[flag: 这个决定的代价是 ROS 侧失去了"单独跑 MFE 做消融"的能力。消融属于阶段一，阶段一已经做完了（SPEC §8.12–8.25）。阶段二不需要在 ROS 里做消融。若后续要加，加一个 `--stages mfe` 的 sidecar 参数即可，不用改架构。]`

### 11.2 节点职责与话题契约

| 节点 | 语言 | 职责 | 订阅 | 发布 |
|---|---|---|---|---|
| `tt_driver` | py3.8 | Tello/TT 视频流接收、飞控指令下发、状态回传；支持 `source:=file` 回放视频文件 | `/tt/cmd_vel` | `/camera/image_raw`、`/tt/state` |
| `mav_node` | py3.8 | 把帧发给 sidecar，把检测转成 ROS 消息 | `/camera/image_raw` | `/mav/candidates`、`/mav/detections` |
| `tracker_node` | py3.8 | SORT 轨迹关联、ID 管理、状态机 | `/mav/detections` | `/mav/tracks` |
| `viz_node` | py3.8 | 画面叠加、HUD、RViz marker | `/camera/image_raw`、`/mav/candidates`、`/mav/tracks` | `/mav/debug_image` |
| `mission_node` | py3.8 | 跟踪任务编排、视觉伺服、失控保护 | `/mav/tracks` | `/tt/cmd_vel` |
| `detect_server.py` | **py3.11** | MFE→TF→LAC→LAD 全链路（直接调 `mgmd.pipeline` 的组件） | socket | socket |

**为什么 mav_node 和 detect_server 要拆开，而不是让 sidecar 直接发 ROS 消息？**
sidecar 是 3.11，发不了 ROS1 消息（没有 rospy）。它只能说 socket。`mav_node` 是纯胶水，职责单一，坏了容易定位。

**话题契约**（"易于扩展"的实际载体，E1/E2 靠它成立）：

| 话题 | 消息类型 | 频率 | 说明 |
|---|---|---|---|
| `/camera/image_raw` | `sensor_msgs/Image` | 30 Hz | bgr8，960×720 |
| `/tt/state` | `std_msgs/Float32MultiArray` | 10 Hz | `[battery, height_cm, tof_cm, pitch, roll, yaw, vgx, vgy, vgz, temp]` |
| `/tt/cmd_vel` | `geometry_msgs/Twist` | 30 Hz | `linear.x/y/z` 米/秒，`angular.z` 弧度/秒。**Tello 只接受 -100..100 的整数通道值，由 driver 换算** |
| `/mav/candidates` | `mav_tracker_msgs/DetectionArray` | 30 Hz | MFE 原始候选 |
| `/mav/detections` | `mav_tracker_msgs/DetectionArray` | 30 Hz | 精修后检测 |
| `/mav/tracks` | `mav_tracker_msgs/TrackArray` | 30 Hz | 带 ID 轨迹 |
| `/mav/debug_image` | `sensor_msgs/Image` | 15 Hz | 可视化，降频以省带宽 |
| `/mav/track_target` | action `mav_tracker_msgs/TrackTarget` | on-demand | 目标跟踪任务 |

`[flag: 现有 ros2_ws 下的消息定义（4 个 msg + 1 个 action）可以直接复用，字段设计成立。但它从未提交 git。本版要求搬到 ros1_ws 并提交，同时补齐 Float32MultiArray 之外的字段。]`

**为什么用 `Float32MultiArray` 而不是给 Tello 状态定义专用消息？**
Tello 状态字段可能随固件版本变化（TT 比 Tello 多 ToF）。专用 msg 一旦字段变就要重新生成接口。启动阶段用数组 + 文档约定，等字段稳定了再升级成专用 msg。这是**故意的技术债**，记在 §11.9 技术债表。

### 11.4 六个必须提前接受的约束

每条都改验收标准。

#### 约束 1：空中对空中，需要 ≥2 架（Q20 已解决）

TT 相机朝前，**看不到自己**。要让 TT 检测"小目标无人机"，天上必须有第二个飞行物。

**Q20 回答：实验室有多架。** 这条从风险降为已解决，但仍有两个衍生问题：

| 衍生问题 | 应对 |
|---|---|
| 目标机是什么型号？与 TT 外观差异多大？ | 若与 TT 同型号最好（外观域一致度高）。若不同型号，LAC/LAD 微调必须覆盖该机型 |
| 两架飞机都吃 WiFi 图传，信道冲突 | 一架设 5.8 GHz，一架设 2.4 GHz；或错开时间起飞 |

#### 约束 2：域差异可能让现有权重直接失效

| 维度 | ARD-MAV（训练域） | TT（实机） |
|---|---|---|
| 视角 | 机载**俯视** | **前视**，近水平 |
| 分辨率 | 1920×1080 | 960×720 |
| 目标尺寸 | 中位 13×9 px | 距 10 m 时 TT 约 25×25 px，距 30 m 时约 8×8 px |
| 目标类型 | 多机型 | 实验室机型 |
| 背景 | 城市/建筑/树木 | **室外天空 + 地面 + 建筑** |
| 干扰 | 相机自身运动 | **风致云台抖动 + 飞鸟** |

**已有证据**：MVDT（静态地面相机）测试时 MFE 跨域可用（召回 97%），**LAC 完全失效**（D1 从 99.5% 掉到 1.0%，GT 处 P(MAV) 仅 0.0002，SPEC §8.26）。

**推断**：室外前视与俯视的差异不小于 MVDT。**现有权重很可能直接失效。**

**应对**：阶段二必须含"用 TT 实拍室外数据重训/微调 LAC 与 LAD"，**工时 5 天**，不能假设直接可用。这是阶段二最大的单项工时，已计入 §11.7。

#### 约束 3：三帧差分带来 k 帧延迟

MFE 的 OR 模式需要 `I_{t-k}` 与 `I_{t+k}`，**必须等未来 k 帧**才能处理第 t 帧。

| 模式 | 延迟 | 召回（ARD-MAV 实测，SPEC §8.11） |
|---|---|---|
| `2frame` | **0 帧**（因果） | 33.9% |
| `3frame_or` | k 帧（k=1 时 33 ms） | **78.2%** |

**取舍是真的**：控制回路里 33 ms 可接受，但 OR 模式不是因果的，不能在流式场景里"立刻出结果"。

**要求**：`mav_node` 必须提供 `causal` 参数。`true` 时 sidecar 用 2frame（零延迟，低召回），`false` 时用 3frame_or（k 帧延迟，高召回）。

#### 约束 4："实时"受限于 WiFi 图传，不是 GPU

| 环节 | 估计延迟（室外） |
|---|---|
| TT 相机采集 + H.264 编码 | 30–50 ms |
| WiFi 传输（室外 2.4/5.8 GHz，距离 < 30 m） | 50–150 ms |
| 解码 | 10–20 ms |
| 检测（3.11 + GPU，阶段一实测 19–137 ms） | 19–137 ms |
| 控制指令下发 | 20–50 ms |
| **端到端** | **约 130–400 ms** |

**验收标准不写"30 FPS"，写"端到端延迟 < 400 ms"**，并单独报告分段耗时。检测再快，WiFi 是天花板。

#### 约束 5：没有机载算力，也没有深度

- 所有计算在地面站（笔记本）。**室外飞场要保证笔记本在 WiFi 内（< 50 m 更稳）**。
- 无深度，距离估计只能靠框面积反推（TT 是 82.6° 视场角，可用针孔模型近似，误差 ±30%）。
- 跟踪只能是**视觉伺服**（把目标拉回画面中心），不能是"飞到某坐标"。

#### 约束 6：室外飞行安全（Q23 新增）

v4.0 假设室内，v4.1 是室外。多变出四条：

| 风险 | 后果 | 软件必须做的事 |
|---|---|---|
| **WiFi 丢包/断连** | 视频流卡死，视觉伺服继续发错误指令 → 撞机 | 连续 500 ms 无新帧 → `mission_node` 立即发零速度；连续 2 s → 触发 `land` |
| **风扰导致 MFE 候选爆炸** | 云台抖动被当成运动，候选数从 25 涨到 500+，FPS 崩到 2 | `n_candidates` 超过阈值（200）时自动降级：关掉 LAD 只跑 LAC，并告警 |
| **逆光 / 强光过曝** | 差分阈值 5 失效，目标淹没 | 室外必须重标定阈值（阶段 C，§11.7）；提供 `mfe_threshold` ros param |
| **飞鸟 / 行人** | 误检进入跟踪，导致飞机追人 | 视觉伺服只在 `state == CONFIRMED` 且 `hits >= 5` 时启动；目标框面积 > 画面 5% 时立即停追（近距离目标不是小目标，是危险） |

**最下面那条不是可选项。** 室外飞场有人，追着人飞是事故。这条写成硬性 gate，不允许配置关闭。

| **sidecar 协议正确性** | 帧进 → 检测出，与直接调用 `pipeline` 结果一致 | 对拍脚本，框位置差 < 2 px |
| **离线重放** | rosbag 跑完整链路，与阶段一脚本输出对拍 | 框中心差 < 2 px，检出帧数差 < 2% |

#### L2 系统级（接真机但不起飞）

| 指标 | 目标 | 备注 |
|---|---|---|
| 相机取帧率 | ≥ 25 FPS（960×720） | 低于 25 就要查 WiFi |
| 端到端延迟 | **< 400 ms** | `header.stamp` 与渲染时刻对比 |
| 检测帧率（全链路） | ≥ 10 FPS | 阶段一 1080p 是 7–15 FPS |
| 长时间稳定性 | 连续 10 分钟不丢帧、不内存泄漏 | `rostopic hz` + `ps` 内存监控 |
| 检测召回（TT 实拍室外） | **先测量，不预设目标** | 测出基线后再定改进目标 |

#### L3 飞行级（起飞后，室外场地）

| 指标 | 目标 | 备注 |
|---|---|---|
| 目标检出率 | ≥ 60%（目标在画面内且距 5–25 m） | 低于则回去调 LAC/LAD |
| 跟踪保持时间 | 连续跟踪 ≥ 5 s 不丢 | 按 `track_id` 不变计 |
| 视觉伺服收敛 | 目标从边缘拉回中心 ±15% 画面宽，用时 < 3 s | 需无风或微风条件 |
| 失控保护 | 丢帧 500 ms 急停、2 s 降落；框面积 > 5% 立即停追 | **强制项，不可配置关闭** |
| 炸机次数 | **0** | 一次就算失败 |

#### 三条不做什么

| 不做 | 原因 |
|---|---|
| 目标三维定位 | 无深度、无 GPS，做不了。框面积反推能给的 ±30% 误差不够用 |
| 自主避障 | 与检测跟踪无关 |
| 多目标同时跟踪 | 论文本身偏单目标。多目标会成倍拉高 `n_candidates`，室外稳定性会崩 |
