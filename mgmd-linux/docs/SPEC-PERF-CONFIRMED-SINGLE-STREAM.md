# 确认轨迹复用下的单流对照

`spec_version: 0.1.1` · `branch: exp/confirmed-single-stream` · `base: master@a6729bd`

`track_gpu.launch compute_lanes:=1` 将灰度准备、MFE、TF、LAC 和 LAD 放入一条 CUDA 计算流。MFE、TF 和模型处理在同一个工作线程上按提交顺序执行。`compute_lanes:=2` 使用基线的两条计算流和一条共享 TF 流，也是实验分支的默认值。实验保留主分支的跨窗口灰度缓存、BUF 连通域、源帧率实时选帧、空闲派发和 `confirm_frames:=3`。CUDA 解码和预览是单独的输入输出环节，沿用原实现。

两次回放统一使用 `phantom30` 1920×1080、`30000/1001` 源帧率、12 个预热窗口、透明 CUDA HUD 和 Windows 原生 FFplay。两组只切换 `compute_lanes`，记录处理和跳过窗口、FPS、各阶段耗时、轨迹复用量、源帧到 ROS 发布延迟和显卡采样。

两组均读入 1,498 帧，正常跑完并确认 FFplay 显示窗口。GPU 指标每 200 ms 采样，表中显存峰值取正式回放区间。

| 指标 | 双流 | 单流 |
|---|---:|---:|
| 实际 FPS | 22.68 | 18.70 |
| 处理 / 跳过窗口 | 1,134 / 362 | 935 / 561 |
| 源帧到 ROS 发布 P50 / P95（ms） | 131.03 / 193.69 | 101.58 / 150.44 |
| GPU 平均占用 | 57.78% | 48.55% |
| 回放显存峰值（MiB） | 1,478 | 1,044 |
| 发布队列采样峰值 | 4 | 1 |
| 含轨迹复用的窗口 | 766 | 611 |
| MFE / TF / LAC / LAD 均值（ms） | 43.85 / 3.42 / 9.57 / 19.19 | 28.92 / 2.20 / 4.52 / 11.21 |

单流吞吐下降 17.5%，发布 P95 下降 22.3%。单流各阶段计时跨度更短，但只有一个窗口能执行检测计算，双流可重叠不同窗口。两种模式各跑一轮，实时跳过的帧不同，阶段耗时和检测结果未在同一帧集合上对拍。[实测摘要](../outputs/confirmed_single_stream_20261119/_summary.json)

## RANSAC 竞争诊断

2026-11-19 在 RTX 3050 Laptop GPU 上先固定输入窗口，再隔离 RANSAC。ROS 诊断关闭实时节拍，`limit:=302`，按单、双、双、单顺序各处理同一组 300 个窗口且无跳帧，保留三帧确认和 CUDA 图像合成。此诊断的 FFplay 未连接，吞吐只用于本组内对照。

| 指标 | 单流两轮 | 双流两轮 |
|---|---:|---:|
| 全组 FPS | 23.66 / 23.97 | 28.31 / 29.09 |
| MFE 均值（ms/窗口） | 23.94 / 23.97 | 35.32 / 34.46 |
| RANSAC 均值（ms/窗口） | 6.346 / 6.286 | 11.478 / 10.776 |

固定源帧后，双流 RANSAC 仍比单流慢约 76%。随后从相同视频的首 8 张解码帧提取 12 组真实的前向和后向 LK 点。每种子设置各做两轮并反转单双顺序，每轮每条流记录 144 次单方向 RANSAC。CUDA Graph 版本将尺度常量提前放到显存，两条流使用不同的捕获及工作区。全部 12 组输出在两条流上均与原实现逐元素完全一致。

| 固定 LK 子实验 | 单流 CUDA 事件均值（ms/方向） | 双流 CUDA 事件均值（ms/方向） |
|---|---:|---:|
| 原始 PyTorch 提交 | 2.647 / 2.730 | 3.538 / 3.587 |
| 缓存尺度常量后提交 | 1.998 / 2.601 | 3.132 / 3.251 |
| CUDA Graph 重放 | 0.930 / 0.935 | 1.305 / 1.302 |

Graph 重放时，双流阶段跨度仍增长约 40%，而每次主机提交约 0.04 ms，支持 GPU 端并发调度或资源竞争是因素之一。双流每批提交两个同类任务，两条都完成的墙钟约 1.47–1.48 ms，单流每批一个约 1.00–1.01 ms。完整流水线还混合其他 GPU 阶段，这个微基准不能直接换算完整链路的竞争占比。

Nsight 在当前 WSL/Docker 环境采到了 CUDA API，CUDA 内核表缺失。标记尺度常量构造后，原版 32 次正式 RANSAC 调用出现 32 次 `cudaStreamSynchronize`，合计 21.993 ms；缓存常量后同样 32 次调用中未观察到该同步。同步 API 的耗时可包含此前已经提交到该流的 GPU 工作，不能与 CUDA 事件耗时相加。现有记录无法进一步判定 SM 算力、显存带宽或哪一类内核的贡献。

只在诊断副本中缓存尺度常量，按双、单各复测同一组 300 个窗口。RANSAC 均值为单流 5.160 ms、双流 10.509 ms，MFE 均值分别为 22.76 和 34.44 ms，吞吐分别为 24.21 和 28.98 FPS。消除一处同步后，双流仍明显慢于单流。完整链路的同步试验每组只跑一遍。[诊断摘要](../outputs/ransac_contention_20261119/_summary.json)
