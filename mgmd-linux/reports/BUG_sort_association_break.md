# BUG 报告：SORT 关联对运动目标在出现后第 2 帧断链

**位置**：`mgmd/tf.py`（`SortTracker.update`）+ `mgmd/kalman.py`（`KalmanBox`）
**严重度**：高 —— 直接摧毁轨迹生成层，进而使 Algorithm 1（III-B2）无法工作
**发现日期**：2026-10-29
**状态**：已复现、已定位根因、修复方案已验证；**尚未修改代码**

---

## 1. 摘要

当目标运动速度超过约 **5.4 px/帧**（10×10 检测框）时，SORT 在目标**首次出现后的第 2 帧**就关联失败，
此后每帧新建一条轨迹，`track_id` 每帧递增，轨迹池无界增长。滤波器本身工作正常
（`KalmanBox` 能准确估计到 20 px/帧 的速度，误差 0.31 px/帧），失败发生在
**"新轨迹只有一次观测、速度未初始化"** 与 **"IoU 关联阈值 0.3 对位移的容忍度有限"** 这两者的组合上。

---

## 2. 现象

### 2.1 复现脚本

```python
import numpy as np
from mgmd.tf import SortTracker, iou

for v in (2, 3, 5, 7, 10, 15, 20):
    tr = SortTracker(d_mode="self", d_min=0.0)
    ious, n_ids = [], set()
    for f in range(1, 13):
        det = ((f-1)*v, 50.0, (f-1)*v + 10.0, 60.0)     # 10x10 方框，匀速
        pred = {tid: tr._kal[tid].predict() for tid in tr.states}
        if pred:
            ious.append(max(iou(p, det) for p in pred.values()))
        tr.update([det], f)
        n_ids |= set(tr.states)
    print(f"v={v:>2}  帧2 IoU={ious[0]:.3f}  稳态 IoU={ious[-1]:.3f}  轨迹数={len(n_ids)}")
```

### 2.2 输出

```
    v    帧2 IoU    稳态 IoU     轨迹数
    2     0.667     0.818       1
    3     0.538     0.739       1
    5     0.333     0.600       1
    7     0.176     0.176      12
   10     0.000     0.000      12
   15     0.000     0.000      12
   20     0.000     0.000      12
```

**分水岭在 5 和 7 之间。** 超过之后不是"变差"，而是完全失效：稳态 IoU 恒为 0，
轨迹数等于帧数减一（每帧一条新轨迹）。

### 2.3 逐帧轨迹

`v=7`，10×10 框：

```
 帧   观测cx   预测cx   预测误差    估计vx     IoU
  1     0.0       -         -        -       -
  2     7.0     5.00     -2.00     0.000   0.176   ← 断链点
  3    14.0     5.00     -9.00     0.000   0.000
  4    21.0     5.00    -16.00     0.000   0.000
  5    28.0     5.00    -23.00     0.000   0.000
  6    35.0    12.00     -23.00     0.000   0.000   ← tid1 被删，tid2 起来
```

预测框从第 2 帧起"卡"在 `cx=5`，因为该轨迹此后再没匹配上过，速度从未被更新。

---

## 3. 根因

### 3.1 失配链条

`SortTracker.update()` 的第 1→2 帧：

```
帧 1  ── 无已有轨迹 ──> 走"新建轨迹"分支（tf.py:268）
                        KalmanBox(box)  →  x = [cx, cy, s, r, 0, 0, 0]
                                                        ↑ 速度为 0（合理，无信息）

帧 2  ── predict() ──>  cx += vx*1 = cx + 0     预测框原地不动
        检测框已移动 v 像素
        IoU = IoU(位移 v, 框宽 10)
        IoU < 0.3  →  匹配失败
        trace 进 "未匹配轨迹：老化" + "新建轨迹"  →  又得到一条 vx=0 的轨迹
```

**关键在最后一步**：关联失败不只是漏了一帧，它同时**切断了新轨迹获得第二次观测的唯一机会**。
速度需要至少两次观测才能估计，而第 2 帧失败后这条轨迹再也不会有第二次观测。
这个循环是**自我维持、无法逃逸的**。

### 3.2 为什么阈值切在 5.4 px

对两个边长为 `w` 的方框，中心沿一轴平移 `d`（`d < w`）：

```
IoU(d, w) = (w - d)·w / (2w² - (w - d)·w)
```

令 `IoU = 0.3` 反解 `d`：

| IoU 阈值 | w=8 | w=10 | w=20 | w=40 | w=60 |
|---|---|---|---|---|---|
| 0.5 | 2.67 | 3.33 | 6.67 | 13.33 | 20.00 |
| 0.3 | 4.31 | **5.38** | 10.77 | 21.54 | 32.31 |

所以 `iou_thresh=0.3` 对 10×10 目标等价于 **"单帧位移必须 < 5.38 px"**。
这不是 Kalman 的问题，是 IoU 度量在高帧率/小目标场景下的固有分辨率极限。

### 3.3 滤波器本身没有问题

单独测试 `KalmanBox`，按正确顺序交替 `predict()`/`update()`：

```
真值 v=  2.0px/帧 -> 估计 vx=   1.969   误差=0.031
真值 v=  5.0px/帧 -> 估计 vx=   4.922   误差=0.078
真值 v= 10.0px/帧 -> 估计 vx=   9.843   误差=0.157
真值 v= 20.0px/帧 -> 估计 vx=  19.687   误差=0.313
```

`F`、`H`、`R`、`Q`、`P` 的构造与 SORT 参考实现（Bewley et al. 2016）一致，
速度维增益正常。**故障不在 `kalman.py`。**

### 3.4 若能扛过第 2 帧，速度会立即接管

强制保持关联不断（理想情形）时的预测误差演化：

```
v=7 :  帧3 误差 2.94px IoU=0.658 vx=5.35   → 帧4 起稳定匹配
v=20:  帧3 误差 0.88px IoU=0.259 vx=15.29  → 帧4 IoU=0.532 起匹配
```

滤波器有能力跟上 20 px/帧，**只是拿不到第二次观测来启动**。

## 4. 影响面

| 影响 | 说明 |
|---|---|
| 轨迹生成（III-B1） | 高速目标完全无法形成轨迹；`track_id` 每帧递增 |
| 轨迹分类（III-B2） | `TrackState.lifetime` 永远 < 3，`classify()` 恒返回 `lifetime_lt_3`。**Algorithm 1 在整个高速序列上零输出** |
| 召回率 | 高速段召回直接归零，且不会体现为"D 不达标"而是"轨迹太短" |
| 轨迹池 | 每帧 +1 条，`max_age=3` 只能压到 4 条，但全是垃圾轨迹 |
| `pipeline.py:96` 注释 | "避免 SORT 轨迹池爆炸，先 LAC 再 TF" 的优化实际在**掩盖**本 bug；关联正常时池子本不会涨 |
| 既有测试 | `tests/test_tf.py` 全部 15 个用例通过，因为运动测试统一用 **5 px/帧**（`test_sort_confirms_moving_track` 等），恰好落在阈值以下。**测试盲区** |

### 4.1 为什么测试没抓到

`tests/test_tf.py` 里所有运动类用例的速度都低于 5.4 px/帧 这条线：

| 用例 | 速度 | 框尺寸 |
|---|---|---|
| `test_sort_confirms_moving_track` | 5 px/帧 | 10×10 |
| `test_sort_max_age_deletes_track` | 3 px/帧 | 10×10 |
| `test_no_coasting_output` | 5 px/帧 | 10×10 |
| `test_two_targets_tracked_separately` | ±4 px/帧 | 10×10 |

其中 5 px/帧 的 IoU 恰好是 0.333，只比阈值 0.3 高 0.033——**卡在阈值边缘**。

实测把 `test_two_targets_tracked_separately` 的速度从 4 提到 6 px/帧：

```
4 px/帧：输出轨迹数 = 2（测试断言 2，通过）
6 px/帧：输出轨迹数 = 0（应为 2），轨迹池 = 8 条垃圾轨迹
```

**测试通过完全依赖速度恰好落在阈值以下，而不是逻辑正确。**

---

## 5. 修复方案

分两层，必须都做才完整（第 2 帧的误差无法靠速度初始化消除）。

### 5.1 第一层：用前两帧差初始化速度（解决问题的主体）

新轨迹在第 2 帧被匹配上时，用"第 1 帧框 → 第 2 帧框"的差分直接写入速度分量。
不要等滤波器自己收敛——滤波器收敛需要 2~3 帧，但关联只给一次机会。

改动点：`SortTracker` 维护每个 `tid` 的"上一观测框"，`KalmanBox` 增加可选的速度初值。

```python
# kalman.py
def __init__(self, box, prev_box=None):
    ...
    if prev_box is not None:
        a = self._box_to_z(prev_box).ravel()
        b = self._box_to_z(box).ravel()
        for i, j in ((4, 0), (5, 1), (6, 2)):
            self.x[i, 0] = b[j] - a[j]      # 假定 dt=1 帧
```

**验证结果**（第 3 帧的预测 IoU）：

| 速度 px/帧 | 现状 | 速度初始化后 |
|---|---|---|
| 5 | 0.333 | **1.000** |
| 7 | 0.176 | **1.000** |
| 10 | 0.000 | **1.000** |
| 20 | 0.000 | **1.000** |
| 40 | 0.000 | **1.000** |

### 5.2 第二层：第 2 帧需要更宽的关联判据

第 2 帧只有一次观测，任何速度初始化都无从谈起，此时预测框必然落后一帧位移。
三个可选做法：

- **新生轨迹用更低的 IoU 阈值**（如 0.1）——最贴近原 SORT 实现（原版 `iou_threshold=0.3` 但
  其 `KalmanBoxTracker` 构造时已跑一次 update，行为略有不同）；
- **IoU 与中心距离的混合代价**，距离门控用"不超过框对角线"之类与尺度无关的量——
  更适合 MFE 候选框尺寸变化大的场景；
- **改用 GIoU / DIoU**，它们在无重叠时仍有梯度，能接住大位移。

推荐 **IoU + 中心距离混合**：与框尺寸挂钩，不需要引入新依赖，且对 `pipeline.py` 的调用签名零改动。

### 5.3 不要做的事

- **不要只调大 `max_age`**：它延长垃圾轨迹的存活，但第 2 帧仍然断链，轨迹池只会更脏。
- **不要只调低 `iou_thresh`**：全局放宽会让相邻目标互串，多目标场景下引入 ID switch。
- **不要动 `Q`/`R`**：滤波器方程本身正确，调噪声超参解决不了"只有一次观测"的信息缺失。

## 6. 建议的验证

1. **回归测试**：速度扫描 1~40 px/帧，断言 `轨迹数 == 1` 且 `lifetime` 单调增长。
2. **测试补齐**：把现有运动类用例的参数化到多个速度，暴露 5 px/帧 这个盲点。
3. **真实序列**：在 ARD-MAV 上统计 MFE 候选框的帧间位移分布，确认实际速度是否越过 5.4 px/帧。
   若 MFE 输出的小目标位移普遍在 10~30 px/帧，则本 bug 意味着**之前所有 TF 实验结果都无意义**。
4. **ID switch 指标**：当前 `metrics.py` 没有任何 track id 相关的度量，无法量化换 ID 损失。
