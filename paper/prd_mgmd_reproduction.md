## 1. Executive Summary

我要在 **ARD-MAV 数据集**上复现 MGMD 三模块流水线（MFE 运动特征增强 → TF 轨迹过滤 → LAC 局部外观分类 → LAD 局部外观检测），产出可直接与论文 Table 1 / Table 2 / Table 3 并排对比的表格，并提交一份逐项说明"哪些数字可比、哪些不可比"的偏差报告。

**这份 PRD 的核心不是"照着写代码"，而是先定义"什么算复现成功"。** 这篇论文没有发布官方代码、没有给出帧间隔 k、没有说明 LAC 训练样本如何构造、没有定义 AP 的计算方式。

好消息是：**测试集划分已经找到了**。论文正文只说"50 训练 / 10 测试"不给 ID，但同组 GLAD 仓库的 README 公开了 15 个测试视频 ID 并按 Ordinary/Complex/Small 分了三档，这 15 个视频在本地数据里全部齐全。所以我们不用自建划分。

坏消息是：**论文的 D≥1 判据数学上不可达**（我用 28,096 对真实 GT 验证，0 个通过，见 §6.0）。这是复现过程中发现的论文缺陷，本身要作为结论报出来。

结论先行：**论文数值不可能逐位对齐，但三张表的趋势和量级可以复现。** PRD 以此为验收基准（§6），超出带宽即判失败并强制归因。

### 1.1 阶段二：从离线复现到实机系统（本版新增）

阶段一交付的是"在别人的数据集上把论文跑出来"。阶段二要把同一套算法搬到真实旋翼平台上：

> 利用 DJI RoboMaster TT 四旋翼无人机，使用基于其 Python SDK 的 ROS 驱动，实现单目旋翼无人机小目标检测与跟踪。各功能以 ROS 节点形式模块化实现，完成易于扩展的检测跟踪软件框架。

**这不是"加个摄像头读帧"那么简单。** 三个变化会重构整个交付物：

| 变化 | 阶段一 | 阶段二 |
|---|---|---|
| 输入 | 1080p 机载俯视数据集 | 960×720 前视 WiFi 视频流 |
| 运行方式 | 离线批量处理 | 在线逐帧，有硬延迟上限 |
| 交付形态 | 脚本 + 报告 | 可启动的组合式软件系统 |
| 失败代价 | 指标不好看 | 飞机撞墙 |

结论先行：**阶段二的主要风险不在算法，在两件事。一是"空中对空中检测需要两架无人机"这个物理前提；二是 Tello 相机与 ARD-MAV 数据集的域差异可能让现有权重直接失效。** 详见 §11.4。

## 2. Problem Statement

**谁有这个问题**：我自己，一个人做毕业设计的复现者。手上有论文 PDF/Markdown、有一台消费级笔记本（RTX 3050 4 GB，已实测够用）。工时估算约 34 人天 ≈ 5.5 周（§9.1b，含代码复用）。

**问题是什么**：论文给的是方法描述 + 三张结果表，缺的是可执行规格。缺失项不是边角料，是决定结果的参数：

| 缺失项 | 影响 | 论文是否提及 |
|---|---|---|
| 帧间隔 k（当前帧与前后各 k 帧做差分） | 直接决定 MFE 能否检出 8×8 像素目标 | ❌ 完全未给 |
| 测试集划分（论文只说 50 训练 / 10 测试） | 论文未给 ID，**但 GLAD README 给了 45/15 及 15 个 ID** | ⚠️ 论文未给，同组仓库给了（且两者数字冲突） |
| LAC 正负样本构造方式 | 决定 LAC 能否学到 MAV 与杂波边界 | ❌ 未说明 |
| LAD "小目标检测层"具体接法 | 只说"浅层与深层 concat" | ⚠️ 一句话，无结构 |
| AP 计算口径（按帧累积 vs 按视频） | 0.55 这个数字无从核对 | ❌ 未说明 |
| FPS 是否含预处理 | 28 FPS 的边界不明 | ❌ 未说明 |

## 4. Strategic Context

**为什么现在做**：数据已齐全（60 视频 / 107,497 XML，与官方 README 逐数字核实）、权重已下载、官方测试集划分已拿到、论文的 D 判据缺陷已定位。前一个工程失败的原因也清楚了（见下）。这是把所有不确定性清掉之后，第一次可以干净地重做。

**前一个工程（`…/mgmd/`）的失败模式，是本项目最重要的输入**：

| 它做了什么 | 为什么失败 |
|---|---|
| MFE 跑出 71.2% 召回 | 但其中混入了四项论文没有的额外约束（高斯模糊、位移过滤、面积上限、长宽比），无法归因 |
| TF 判据 D≥1 跑不通 | 没有停下来问"是不是公式本身有问题"，而是改了实现 |
| 最终放弃 | — |

**`tracking/` 是另一个前项目，失败模式不同但同样有参考价值**：

| 它做了什么 | 为什么不能用 |
|---|---|
| 把 `alg1_d_min` 从 1.0 降到 0.002–0.1，每序列一个值 | 实测降阈值后 Algorithm 1 只剩 **0.59%** 剔除率，机制等于关掉；且对着测试集调参 |
| 加了论文没有的 `ever_confirmed` 粘性标志 | 偏离论文，未声明为偏离 |
| MVDT 上跑到 95.96% recall | 点 GT + 半径 100px 匹配，与论文框 GT + IoU 0.25 口径不可比 |

**所以本项目的核心战略是：把"方法是否奏效"和"参数是否调对"彻底分开。** 具体三条：

1. **额外约束必须做开关对照**。任何论文没有的步骤，都要给出"开 vs 关"两行数字。
2. **阈值只能从训练集标定**，测试集不参与，且全测试集用同一个值。
3. **论文原值必须报**。`d_min=1.0` 那行如实写"0 条轨迹通过"，这是论文缺陷的直接证据，不是我们的失败。

**对照格局**（论文 Table 1 的 5 条基线，需同条件重跑）：YOLOv5s、TPH-YOLOv5s、TPH-YOLOv5l、Dogfight（CVPR'21）、MEGA（CVPR'20）。

## 5. Solution Overview

### 5.1 复现流水线（四模块，二阶段策略）

```
ARD-MAV 视频 + VOC XML
        │
        ▼  [新增] 数据适配层：视频 ↔ XML 帧号对齐，统一 GT CSV
        │
        ▼  MFE ── 网格 LK + RANSAC 单应 → 多帧差分（k 可配）→ OR 聚合 → 形态学 → 连通域
        │
        ▼  TF  ── SORT（IoU 0.3、max_age 3、min_hits 1）+ Algorithm 1（ρ/d ≥ d_min，双模式）
        │
        ▼  LAC ── 32×32 三层 CNN 二分类（阶段A 官方权重 / 阶段B 自训）
        │
        ▼  LAD ── 320×320 裁剪 + YOLOv5s(+小目标层)（阶段A 官方权重 / 阶段B 自训）
        │
        ▼  [新增] 评测层：IoU 0.25 匹配 → P/R/F1/AP/FPS
        │
        ▼  Table 1 / Table 2 / Table 3 + 偏差归因报告
```

**阶段 A（第 1–4 周）**：用 GLAD 仓库官方权重（在 ARD-MAV 上训练）跑全流水线，先拿到端到端基线。目的不是"复现成功"，而是**证明评测链路正确**：如果阶段 A 的 F1 已经掉到 0.4 以下，问题在评测或数据对齐，不在训练。

**阶段 B（第 5–5.5 周）**：按论文配方自训 LAC（Adam lr=0.001、100 epochs、batch=64、32×32）与 LAD（YOLOv5s + 小目标层、Adam momentum=0.937、lr=0.01、MS-COCO 预训练、320 裁剪）。阶段 A 与 B 的结果**并列呈现**，不合并。

### 5.4 多目标支持（Q2 已确认，但实测占比极低）

**先给实测事实**：60 视频集 107,497 帧里，含 2 个目标的只有 **18 帧**（0.017%），无 3 个及以上目标的帧。

所以这条路线的成本收益要说清楚：

| 项 | 判断 |
|---|---|
| 数据集是单目标还是多目标？ | **事实单目标**（99.98% 的帧只有 1 个目标） |
| 还要不要实现多目标评测？ | **要**。你的要求明确，且代码成本低（约 1 天），不做等于评测器有已知缺陷 |
| 分组报告会不会空？ | 2–3 个目标组只有 18 帧，≥4 个目标组 **0 帧**。报告中如实标注"样本不足，不外推" |

**实现要求不变：**

| 项 | 单目标帧 | 多目标帧 |
|---|---|---|
| 每帧输出 | ≤1 框 | 全部通过模块的候选，不做 top-1 截断 |
| GT 匹配 | 匈牙利一对一 | 匈牙利一对一（同一算法） |
| 空帧处理 | 检测到即 FP | 同左 |

**评测器的三个硬要求**：
1. 匹配必须是**一对一**。贪心匹配在密集场景会重复吃同一个 GT，虚高 precision。
2. 必须输出**每帧检测数分布**（0/1/2/3+）与 GT 数分布，作为"是否靠多发框换 recall"的护栏。
3. 按 GT 数分组报告，但小组样本量必须同时列出。18 帧的组不能拿来下结论。

## 6. Success Metrics

### 6.0 两个必须先解决的已发现问题（决定复现是否成立）

你已有的实测数据暴露了两个**结构性矛盾**，它们比"跑出多少 F1"更重要。这两个不解决，Table 1/3 数字没有意义。

**问题 A：论文的 D≥1 判据在 ARD-MAV 上数学不可达（已独立验证，非引用）**

论文英文原文（`paper_mgmd_en.md` 第 118 行）定义：

> $d(b_i,b_j)$ represents the diagonal length of the **smallest enclosing box** of $b_i$ and $b_j$.

**证明（纯数学，与实现无关）**：设两框中心距为 ρ，最小外包框宽 W、高 H，对角线 d=√(W²+H²)。
若 b_j 在 b_i 右侧，则 W = (x1j+wj) − x1i，而 ρ = (x1j+wj/2) − (x1i+wi/2)。
两式相减：**W − ρ = (wi+wj)/2 > 0**，故 ρ < W ≤ d，**即 D = ρ/d < 1 恒成立**。
这个不等式对任意框尺寸、任意位移都成立，与数据集无关。

**三重独立验证**：

| # | 验证方式 | 结果 |
|---|---|---|
| 1 | 数学证明（上式） | D < 1 恒成立，仅当框退化为零尺寸点时极限为 1 |
| 2 | 随机生成 20 万组框对 | D 最大观测值 **0.9731**，无一达到 1 |
| 3 | **28,096 对真实 GT**（15 个官方测试视频全部，间隔 3 帧，单目标帧） | D 最大 **0.9610**，`D≥1` 通过 **0 个（0.000%）** |

逐视频最大 D：phantom43 0.9540、phantom58 0.9610、phantom05 0.9073、phantom10 0.8919…… **15 个视频无一有帧达到 1。** 验证脚本：`paper/_verify/realD.py`、`percentiles.py`、`target_motion.py`，可复跑。

**为什么论文能出结果？** 因为 D≥1 隐含了一个前提：**3 帧内位移 ≥ 目标自身尺寸**。实测该前提在 ARD-MAV 上不成立：
位移/尺寸比的 P50 只有 **0.478**，仅 **16.41%** 的样本位移超过自身尺寸。论文的 D≥1 阈值实际等价于只保留"极快运动"的目标。

**D 的真实分布**（N=28,096）：

| 分位 | P50 | P75 | P90 | P95 | P99 | max |
|---|---|---|---|---|---|---|
| D | 0.332 | 0.459 | 0.579 | 0.655 | 0.781 | 0.961 |

若改用标定阈值：thr=0.5 → 保留 18.69%；thr=0.6 → 8.44%；thr=0.7 → 3.20%；thr=0.8 → 0.72%。

`[flag: 这是独立发现，不是"我们实现错了"。论文公式与其阈值 D≥1 在数学上不自洽。必须在报告中作为独立发现列出，并给出标定阈值的对照。]`

**问题 B：MFE 漏检是瓶颈，不在 TF**

实测：phantom63 背景极杂乱（213 候选/帧），phantom76 极干净（7.9 候选/帧），**候选数降 27 倍，轨迹碎片率几乎不变（63% vs 60%）**。

逐帧定位断点：帧 319/325/327 的 MFE **候选数为 0**（完全漏检）；帧 322–323 检出了但框偏大（20×13 vs GT 14×10），IoU 掉到 0.25 以下。

**结论：优化 SORT 关联策略解决不了碎片化。MFE 的检出稳定性必须先解决。** 这直接推翻原 PRD "G1 候选召回 ≥70% 就算过"的设计——70% 的召回意味着 30% 的帧直接无输入。

### 6.0b 一个被推翻的结论：`Net_best.pth` 没有失效

旧工程在 TODO.md 里断言：`Net_best.pth` 对所有输入恒返回类别 0，"权重失效，必须重训"。**这个结论是错的，我推翻了。**

**复验方法**：把 checkpoint 的 fp32 权重直接从 zip 里解出来，用纯 Python 实现一遍前向传播（Conv5×5 → MaxPool2 → Conv5×5 → MaxPool2 → FC400-120-84-2，与官方 `Net` 逐层一致），喂真实数据。

**第一层验证：权重的物理完整性**

| 检查 | 结果 |
|---|---|
| sha256 vs 官方预 pin 值 | ✅ 完全一致 `0d3a4631060339ee...` |
| zip 容器完整性 | ✅ `testzip()` 通过，12 个条目 |
| 各层形状与代码 `Net` 定义对比 | ✅ 10/10 全部匹配（conv1 450、conv2 2400、fc1 48000、fc2 10080、fc3 168） |
| `fc3.bias` | `(-0.0426, -0.0472)`，两个类别偏置几乎相等，不偏袒任何一类 |

**第二层验证：合成图**（与旧工程结论吻合，所以它当时得出了"失效"）

| 输入 | logits | P(MAV) |
|---|---|---|
| 纯黑 | (6.43, −4.56) | 0.000017 |
| 纯白 | (2.90, −2.42) | 0.004869 |
| 纯灰 | (3.78, −3.17) | 0.000961 |
| 随机噪声 | (5.26, −4.30) | 0.000071 |

到这里一切都支持旧工程的说法。**但合成图本来就不是 MAV，网络给低分是正确行为，不是失效。**

## 11. 阶段二：ROS 实机检测跟踪系统

### 11.1 目标

把阶段一的检测算法做成一套**可组合、可替换、可单独测试**的 ROS2 软件框架，跑在 DJI RoboMaster TT 上，完成单目小目标检测与跟踪。

"易于扩展"的具体含义是三条可验证的性质：

1. **换检测器不改其他节点**：把 MGMD 换成 YOLO 或别的算法，只需替换一个节点，话题契约不变
2. **换平台不改算法节点**：把 TT 换成其他无人机，只需替换 driver 节点
3. **离线可复现**：用录制的 rosbag 能重放整条链路，不需要真机

### 11.2 硬件与 SDK 事实

| 项 | DJI RoboMaster TT |
|---|---|
| 相机 | 500 万像素，视频 **960×720 @ 30fps** |
| 图传 | WiFi 2.4/5.8 GHz，H.264 走 UDP |
| 定位 | 无 GPS；下视 ToF + 视觉里程计（仅用于悬停） |
| 控制接口 | Tello SDK 2.0，文本命令走 UDP 8889 |
| 视频接口 | UDP 11111 |
| 状态回传 | UDP 8890，二进制包 |
| 机载算力 | **无**（所有视觉计算必须在外部） |
| 续航 | 约 13 分钟 |

**四条直接影响架构的事实：**

1. **没有机载算力**，检测必须在笔记本/地面站做。所以"实时"的瓶颈是 WiFi 图传延迟，不是 GPU。
2. **没有 GPS 与深度**，无法直接算出目标的真实三维位置。只能得到"目标在画面里的方位"，距离只能靠框面积粗略估计。
3. **控制接口只有速度指令**（`rc a b c d`，四个通道），没有位置控制。所以跟踪只能做**视觉伺服**（把目标拉回画面中心），不能做"飞到某坐标"。
4. **SDK 是文本协议**，没有内置的 ROS 集成。需要用 Python SDK（`djitellopy`）封装成 ROS 节点。

`[assumption: 上述规格来自 Tello/RoboMaster TT 公开资料，实机到货后需逐项核对，尤其视频分辨率与延迟。]`

### 11.3 架构：七个 ROS2 节点

选 ROS2（Humble 或 Jazzy），不选 ROS1。理由：ROS1 Noetic 已于 2025 年 5 月停止维护，新项目没有理由选它。

```
                    ┌──────────────────┐
     WiFi 视频 ────► │ tello_driver     │──► /camera/image_raw
                    │ (djitellopy)     │──► /tello/state
                    └──────────────────┘◄── /tello/cmd_vel
                              ▲
                              │
                    ┌─────────┴────────┐
                    │ mission_node     │◄── /mav/tracks
                    │ (action server)  │
                    └──────────────────┘

  /camera/image_raw
        │
        ▼
  ┌──────────────┐
  │ mfe_node     │──► /mav/candidates   (MFE 原始候选)
  └──────────────┘         │
        │                  │
        └──────┬───────────┘
               ▼
  ┌────────────────────┐
  │ appearance_node    │──► /mav/detections (LAC+LAD 精修)
  │ (LAC + LAD)        │
  └────────────────────┘         │
               ┌─────────────────┘
               ▼
  ┌────────────────────┐
  │ tracker_node       │──► /mav/tracks (带 ID 的轨迹)
  └────────────────────┘
               │
               ▼
  ┌────────────────────┐
  │ viz_node           │──► /mav/debug_image
  └────────────────────┘
```

| 节点 | 职责 | 输入 | 输出 |
|---|---|---|---|
| `tello_driver` | 相机取帧 + 飞控指令下发 + 状态回传 | `/tello/cmd_vel` | `/camera/image_raw`、`/tello/state` |
| `mfe_node` | 帧对齐 + 多帧差分 + 形态学，出候选框 | `/camera/image_raw` | `/mav/candidates` |
| `appearance_node` | LAC 分类 + LAD 精修 | 图像 + `/mav/candidates` | `/mav/detections` |
| `tracker_node` | 轨迹关联、ID 管理、速度估计 | `/mav/detections` | `/mav/tracks` |
| `viz_node` | 画面叠加 + RViz marker | 图像 + 候选 + 轨迹 | `/mav/debug_image` |
| `mission_node` | 跟踪任务编排（action server） | `/mav/tracks` | `/tello/cmd_vel` |
| `replay_node` | 从 rosbag 重放，离线复现 | rosbag | 同 driver |

**为什么 MFE 和 appearance 拆成两个节点**：三者频率不同、失败模式不同。MFE 依赖多帧缓冲（有延迟），appearance 是单帧运算。拆开后可以只跑 MFE 做消融，也可以把 appearance 换成别的实现。

**话题契约**（这是"易于扩展"的实际载体）：

| 话题 | 类型 | 说明 |
|---|---|---|
| `/camera/image_raw` | `sensor_msgs/Image` | 原始帧，bgr8 |
| `/mav/candidates` | `mav_tracker_msgs/DetectionArray` | MFE 候选，含 `n_candidates` 诊断字段 |
| `/mav/detections` | `mav_tracker_msgs/DetectionArray` | 精修后检测 |
| `/mav/tracks` | `mav_tracker_msgs/TrackArray` | 带 ID 轨迹 |
| `/mav/debug_image` | `sensor_msgs/Image` | 可视化 |
| `/tello/cmd_vel` | `geometry_msgs/Twist` | 归一化速度指令 |
| `/mav/track_target` | action `TrackTarget` | 目标跟踪任务 |

### 11.4 五个必须提前接受的约束

这是本节最重要的部分。每一条都会改变验收标准。

#### 约束 1：空中对空中检测需要**两架**无人机

TT 的相机朝前，只能看外部世界。**它看不到自己。**

要让 TT 检测"小目标 MAV"，天上必须有第二个飞行物：另一架 TT、一架玩具无人机，或者至少一个能飞的模型。

| 方案 | 成本 | 问题 |
|---|---|---|
| 两架 TT | 约 ¥2000+ | 最真实的场景 |
| TT + 玩具四旋翼 | 约 ¥200 | 目标外观与训练域差异更大 |
| TT + 悬挂的小目标物 | 约 ¥50 | 静态，测不了运动检测 |

`[flag: 用户原始需求是"单目旋翼无人机小目标检测与跟踪"，但只提到"利用 DJI RoboMaster TT"。若只有一架 TT，能做的是"检测地面/空中的其他飞行器"，而不是"检测自己"。这条必须先确认，否则整个验收标准立不住。]`

#### 约束 2：域差异可能让现有权重直接失效

| 维度 | ARD-MAV（训练域） | Tello（实机） |
|---|---|---|
| 视角 | 机载**俯视** | **前视**，近水平 |
| 分辨率 | 1920×1080 | 960×720 |
| 目标尺寸 | 中位 13×9 px | 取决于距离，可能 20–100 px |
| 目标类型 | 多机型 | 单一特定机型 |
| 背景 | 城市/建筑/树木 | 室内或天空 |

**已有证据**：在 MVDT（静态地面相机）上测试时，MFE 跨域可用（召回 97%），但 **LAC 完全失效**（D1 从 99.5% 掉到 1.0%，GT 处 P(MAV) 仅 0.0002）。

**推断**：Tello 前视 960×720 与 ARD-MAV 俯视 1080p 的差异不小于 MVDT。**现有 LAC/LAD 权重很可能直接失效。**

**应对**：阶段二必须包含"用 Tello 实拍数据重训/微调 LAC 与 LAD"的任务，不能假设直接可用。

#### 约束 3：三帧差分带来 k 帧延迟

MFE 的 OR 模式需要 $I_{t-k}$ 与 $I_{t+k}$，也就是**必须等未来 k 帧**才能处理第 t 帧。

| 模式 | 延迟 | 召回（ARD-MAV 实测） |
|---|---|---|
| `2frame` | **0 帧**（因果） | 33.9% |
| `3frame_or` | k 帧（k=1 时 33ms） | **78.2%** |

**这是一个真实的取舍，不是可以忽略的细节。** 实时控制回路里，33ms 延迟可以接受；但若为了召回降到 k=1 仍要等一帧，控制周期会被拉长。

**建议**：提供 `--causal` 开关。开启时退化为 2frame（零延迟，低召回），关闭时用 3frame（有延迟，高召回）。让用户按任务选。

#### 约束 4："实时"受限于 WiFi 图传，不是 GPU

| 环节 | 估计延迟 |
|---|---|
| Tello 相机采集 + H.264 编码 | 30–50 ms |
| WiFi 传输 | 50–150 ms（受干扰影响大） |
| 解码 | 10–20 ms |
| 检测（GPU，阶段一实测） | 19–137 ms |
| 控制指令下发 | 20–50 ms |
| **端到端** | **约 130–400 ms** |

**结论：即使检测做到 30 FPS，端到端延迟仍在 130–400ms。** 对 1 m/s 飞行的目标，这意味着一帧之间目标移动 13–40 cm。

**因此验收标准不能写"达到 30 FPS"。** 应该写"端到端延迟 < 400ms"，并单独报告各分段耗时。

#### 约束 5：没有机载算力，也没有深度

- 所有计算在地面站。笔记本必须在 WiFi 覆盖内（约 100 m）。
- 无深度信息，距离估计只能靠"框面积占画面比例"反推，误差大。
- 因此跟踪策略只能是**视觉伺服**（把目标拉回画面中心），不能是"保持 3 米距离"。

## 附：与论文的三处已知口径冲突（须在报告中声明）

1. **MFE 差分形式**：论文描述"改进的三帧差分 + 逻辑 OR"，官方 GLAD 实现是"两帧差分 + 自适应阈值"。本 PRD 要求**两套都实现**（US-003 + US-007），Table 2 三档直接对应：2帧=官方口径，3帧+AND 与 3帧+OR=论文口径。这样既不丢论文假设，也不丢可核对实现。

3. **论文称 LAC 为"三层 CNN"**，官方 `Net` 是 2 卷积 + 3 全连接。按官方结构实现，报告中标注差异。

### 阶段二决策（v4.0 新增）

- **框架选 ROS2（Humble 或 Jazzy），不选 ROS1。** ROS1 Noetic 已于 2025-05 停止维护，新项目无理由选它
- **七个节点拆分：driver / mfe / appearance / tracker / viz / mission / replay。** MFE 与 appearance 必须分开，因为前者依赖多帧缓冲（有延迟）、后者是单帧运算，且要支持只跑 MFE 做消融
- **话题契约优先于实现。** "易于扩展"的判据是：换检测器只改一个节点，话题定义不动
- **核心算法以库形式复用，不复制。** `mgmd-linux/mgmd/` 的 mfe/lac/lad/kalman 被节点 import，避免两份代码漂移
- **阶段 A + B（8 天）不依赖硬件，真机到货前必须做完。** 这是降低项目风险的关键安排
- **验收不写"30 FPS"，改写"端到端延迟 < 400ms"。** Tello WiFi 图传决定了这个上限，检测再快也没用
- **阶段二的评测口径与阶段一分开。** 实机没有 GT，不能套 IoU 指标，改用检出率/跟踪保持时间/延迟
